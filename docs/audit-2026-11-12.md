# AUDIT — builderr.ai Signalpost starter kit

- **Tanggal audit:** 2026-11-12 (WIB)
- **Lokasi kit:** `~/workspace/builderr-signalpost/kit/x/signalpost-starter-kit/` (lisensi MIT, © 2026 builderr)
- **Cakupan dibaca:** README.md, OUTPUT_CONTRACT.md, 6 file `docs/*.md`, `pyproject.toml` + `uv.lock`, `select_entry_batch.py`, 25 script `scripts/*.py`, 19 file `src/norway_company_agent/*.py`, `tests/test_poc.py` (1.354 baris), fixtures utama, `data/universe-metadata.json`.
- **Sifat audit:** baca saja. Tidak ada kode diubah, tidak ada data besar diunduh, tidak ada kredensial dipakai.
- **Kontrak skor yang dipakai sebagai patokan (brief koordinator, "evaluation contract v2"):** total 100 = **50** recall & coverage (per field family: 70% company recall + 30% claim recall vs union terverifikasi semua submission + crawler Builderr), **30** precision / exact identity / evidence (wrong-company match material = blokir kualifikasi; tiap klaim wajib sumber + tanggal ambil + periode laporan; nilai hilang JANGAN jadi nol), **12** synthesis, **8** UX. Kualifikasi ≥ 65/100. Satu envelope terminal per input; refresh idempotent; install mesin bersih; tanpa kredensial akun pribadi; biaya API pihak ketiga dideklarasikan (tiebreak).
- **Batasan keras proyek:** GRATIS saja — tanpa API key berbayar / modal / kredensial pribadi. Model ML berat dihindari kecuali terbukti gratis + ringan + reproducible.

## Ringkasan eksekutif

1. **Fondasi resmi sudah kuat, diferensiasi eksternal hampir nol di jalur utama.** `run_competition_batch.py` hanya menjalankan modul BRREG + crawl situs terdaftar + identity gate. Semua konektor jobs/news/reviews/sentiment hidup sebagai script terpisah yang eksperimental/terkarantina dan TIDAK masuk envelope.
2. **Recall terbesar yang gratis justru sudah ada di tangan: bulk CSV BRREG punya 90 kolom, tapi `normalize_row()` hanya memakai ~11.** Email, telepon, deskripsi aktivitas (`aktivitet`), tujuan anggaran dasar, tanggal pendirian, data kapital, kode NACE 2/3, status MVA/kepailitan — semuanya ada di `raw` evidence tapi tidak pernah jadi klaim, tidak masuk research agent, prototype, atau refresh. Ini improvement termurah dengan dampak recall tertinggi.
3. **Envelope saat ini TIDAK cocok dengan OUTPUT_CONTRACT.md.** Tidak ada daftar `claims[]`/`evidence[]` datar, tidak ada `changes[]`/`errors[]`, tidak ada `operations.third_party_cost_usd`, dan kosakata statusnya berbeda. Adapter kontrak adalah pekerjaan wajib (P0) sebelum submit.
4. **Refresh/change-tracking hanya hidup di replay snapshot, tidak terintegrasi ke batch run.** Tidak ada argumen previous-snapshot di `run_competition_batch.py`; `changes` tidak pernah masuk envelope.
5. **Satu-satunya konektor berkunci eksplisit adalah Brave Search API** (`BRAVE_SEARCH_API_KEY`). Tidak ada klien Google Places API di kode sama sekali — yang ada hanya normalizer untuk output scraper Google Maps yang tidak resmi. Semua jalur LinkedIn/Maps/YouTube(yt-dlp)/Fagfolkguiden ditandai eksperimental oleh kit sendiri dan tidak boleh dipromosikan tanpa hak akses.
6. **Ketidakcocokan rubrik yang harus diklarifikasi:** dokumen kit dan `score_competition_v3.py` memakai rubrik 55/15/10/12/8 (external-first), sedangkan brief memakai 50/30/12/8 (v2). Prioritas berubah tergantung mana yang otoritatif — lihat §6, pertanyaan 1.
7. **Sentiment = abstain.** Tidak ada korpus label Norwegia, gate kualifikasi sentiment menuntut ≥300 item berlabel + F1 ≥ 0,80 + presisi ≥ 90%, dan satu-satunya model (NOSIBLE via torch/transformers) berat + `trust_remote_code=True`. Jangan kejar poin sentiment; kejar recall/precision/synthesis/UX.
8. **UX prototype sudah lumayan untuk find/verify, tapi tidak ada compare.** Tidak ada tampilan banding antar-perusahaan, tidak ada section jobs/reviews/news generik (hanya lapisan LinkedIn), dan panel research agent di JS adalah re-implementasi yang menyimpang dari `research.py`.

## 1. Peta pipeline end-to-end

### 1.1 Alur utama (jalur resmi yang dinilai)

```
Batch input (JSON/JSONL/txt, nomor organisasi 9 digit)
  → scripts/run_competition_batch.py
      → batch.read_organisation_inputs()          [validasi: 9 digit, tanpa duplikat; GAGAL TOTAL bila ada input buruk]
      → batch.profiles_from_bulk()                [iter_bulk() atas snapshot CSV BRREG; sha256 seluruh file;
                                                   GAGAL TOTAL bila ada org tidak ada di snapshot]
          → sampling.normalize_row()              [~11 field dari 90 kolom; sisa kolom disimpan mentah di evidence registry]
          → official.accounting_obligation_assessment()
      → ThreadPoolExecutor (default 8 workers), checkpoint tiap 25 profil, --resume
      → per profil, paralel:
          → official.fetch_official_modules()     [5 endpoint live BRREG, modul default; lihat §1.2]
          → website.fetch_website()               [crawl situs dari URL registry; robots.txt; SSRF guard;
                                                   homepage + maks 4 halaman prioritas, domain sama]
          → identity.apply_website_identity_gate()[gate exact-entity; karantina klaim + social link bila gagal]
      → batch.terminal_envelope() per profil      [1 envelope per input; modul apa pun gagal → state per-modul,
                                                   tapi state entitas hanya "submission_error" bila ada modul submission_error]
      → batch.validate_envelopes()                [exact count, unik, semua state terminal, zero silent drops]
  → Output: profiles JSONL + envelopes JSONL + run report JSON (exit 1 bila validasi gagal)
```

### 1.3 Crawl situs (detail `website.py::fetch_website`)

1. `normalize_homepage()` — tambah `https://` bila skema tidak ada; tolak URL non-HTTP(S)/tanpa host.
2. `assert_public_url()` — tolak localhost/`.local`/IP non-global (SSRF guard, termasuk saat redirect via `SafeRedirectHandler`); DNS resolve wajib sukses.
3. `_robots_allowed()` — baca `/robots.txt`; **bila robots.txt tidak tersedia, diasumsikan boleh** (dikomentari di kode sebagai keputusan sadar untuk homepage saja).
4. GET homepage (timeout 15 dtk, maks 2 MB, hanya `text/html`; User-Agent `builderr-signalpost-poc/0.1 (+https://builderr.ai)`). Bila URL registry tanpa skema dan HTTPS gagal → fallback HTTP sekali (rekursi).
5. Ekstraksi: `extruct` (JSON-LD + microdata + OpenGraph) → `_jsonld_organisations()` (hanya tipe Organization/Corporation/LocalBusiness/Store/Restaurant, maks 20); `trafilatura` untuk teks utama (maks 5.000 karakter); `<title>`, meta description; `_social_links()` dari anchor/`data-href`/iframe + `structured_social_links()` dari `sameAs` (catatan: `fetch_website` jalur urllib **tidak** memanggil `structured_social_links` — hanya jalur Scrapy `crawl_events.py` yang menggabungkannya; inkonsistensi, lihat §4).
6. Halaman sekunder: `_priority_links()` memilih maks 4 link same-netloc yang mengandung istilah prioritas (`om-oss`, `about`, `kontakt`, `contact`, `ledelse`, `management`, `team`, `people`, `locations`, `lokasjoner`, `avdelinger`, `butikker`, `news`, `press`, `aktuelt`, `nyheter`); tiap halaman dicek robots + redirect harus tetap dalam registered domain yang sama; maks 1 MB.
7. `extraction_state`: `js_fallback_candidate` bila teks < 100 karakter dan ≥ 2 `<script src>` — **tetapi tidak ada fallback browser yang terhubung**: tidak ada kode yang mengisi `js_fallback` yang dibaca `identity.py`, dan `scrapy-playwright` hanya ada sebagai optional dep tanpa pemakaian. Situs JS-heavy praktis hanya terekam sebagai shell tipis.

### 1.4 Identity gate (detail `identity.py`)

`assess_website_identity()` — deterministik, tanpa fuzzy library (meski `docs/architecture-options.md` menyebut RapidFuzz, RapidFuzz tidak ada di dependensi/kode):

- Tokenisasi nama legal: transliterasi æ/ø/å, buang kata bentuk hukum/generik, token > 1 huruf.
- Skor: org-number persis di evidence homepage → **1,0**; semua token nama legal bersama-sama di satu evidence homepage → **0,95**; token tunggal + homepage substantif (≥100 karakter) → **0,95**; overlap ≥75% & ≥2 token → 0,85; ≥50% → 0,65; lainnya 0,3. Parked-domain marker → 0,1. Kasus khusus klub olahraga perusahaan (B.I.L.) → 0,3 tanpa bukti klub.
- `publishable` hanya bila skor ≥ 0,9 (`exact`); 0,8–0,9 = `review`; di bawahnya `related_or_uncertain`.
- Bila tidak publishable: klaim situs + social link dikarantina (disimpan di `discovered_social_links` + `social_link_assessments`, `social_links` yang dipublikasi dikosongkan).
- **Celah jalur urllib:** `identity_text_excerpt` (teks footer/address — tempat org-number biasanya muncul) hanya diproduksi jalur Scrapy (`crawl_events.py`), bukan `fetch_website()`. Akibatnya bukti org-number di footer tidak terlihat oleh gate di jalur batch default; gate hanya melihat title/description/teks utama/hostname/nama terstruktur. Lihat improvement §4 #11.
- `assess_social_identity()`: handle harus mengandung urutan nama legal ternormalisasi (0,98) atau token dominan (≥0,9 untuk publish).

## 3. Cakupan terhadap dimensi skor

### 3.1 Recall & coverage per field family (50 poin; 70% company recall + 30% claim recall)

| Family | Status | Bukti & celah |

### 3.2 Precision / exact identity / evidence (30 poin)

**Kuat dan ini keunggulan kit — jangan dilemahkan:**

- Org-number sebagai anchor di semua jalur; mismatch identitas ditolak (`refresh.diff_profile` menolak org berbeda; `profiles_from_bulk` memetakan by-org).
- Identity gate deterministik dengan ambang publishable 0,9 + karantina; battery test ekstensif (`WebsiteIdentityTests`: parent/brand/franchise/parked/umbrella ditolak).
- Setiap evidence record membawa `source_url`, `retrieved_at`, `content_sha256` (hash byte mentah), `source_class`/`source_type`, `source_row_key` untuk bulk; status eksplisit membedakan `not_found`/`source_error`/`blocked`/`not_applicable`/`not_fetched`.
- Missing ≠ zero ditegakkan di normalizer, research, dan prototype ("Not reported", "Missing is not zero").
- Periode laporan keuangan dicatat; `effective_at` didukung skema tapi **tidak pernah diisi jalur live** (`http.fetch_json` tidak mengisi `effective_at`) — lihat §5.3.

**Risiko precision yang tersisa:**

1. Gate situs mengandalkan kecocokan nama bila org-number tidak ditemukan di homepage — nama generik/tunggal + homepage substantif bisa lolos 0,95. Mitigasi sudah ada sebagian (token tunggal butuh konten substantif); penambahan cek `vatID`/footer akan memperketat.
2. `_robots_allowed()` mengembalikan True bila robots.txt tidak dapat dibaca — keputusan sadar, tapi perlu didokumentasikan sebagai asumsi di submission.
3. `fetch_json` me-retry 3x dan mengembalikan `status=0` + error generik bila semua gagal — tidak ada pembedaan timeout vs DNS vs 5xx di evidence (hanya string error terakhir).
4. Social-link gate memakai kecocokan substring handle — handle generik (`@oslo`) bisa cocok dengan token nama; ambang 0,9 + syarat gate situs publishable membatasi, tapi tetap titik rawan.
5. Observasi eksternal eksperimental memakai `content_sha256` yang kadang hash dari gabungan string (Google News: hash raw feed + judul + publisher) bukan hash byte sumber yang diklaim — tidak memenuhi definisi hash konten yang sama dengan evidence resmi.

### 3.3 Synthesis (12 poin)

**Hampir tidak ada.** Yang ada:

- `research.answer_profile()`: retrieval deterministik — mengembalikan fakta bersumber per topik + daftar `unsupported_or_uncertain`. Tidak ada narasi "apa yang dilakukan perusahaan, apa yang berubah, apa yang belum diketahui".
- `accounting_obligation_assessment()`: satu-satunya interpretasi beralasan (klasifikasi + reason + ruleset version).
- Prototype: kalimat template JS (`agentBody`) per mode — bukan sintesis atas evidence, dan menyimpang dari logika Python.

**Yang kurang untuk 12 poin:** generator sintesis deterministik per profil (apa yang dilakukan perusahaan dari `aktivitet` + NACE + deskripsi situs; apa yang berubah dari diff refresh; apa yang belum diketahui = daftar family yang `not_available`/`not_found`/`blocked` dengan alasan; setiap kalimat/satuan klaim menunjuk ke evidence). Harus template + aturan, bukan LLM (biaya/determinisme). Lihat §4 #22.

## 5. Format envelope persis + refresh + kesenjangan vs OUTPUT_CONTRACT

### 5.1 Envelope yang dikeluarkan kode saat ini (`batch.terminal_envelope`)

Satu objek JSON per baris di output `--output`. Bentuk persis:

```json
{
  "run_id": "smoke-001",
  "organisation_number": "123456789",
  "state": "complete",
  "started_at": "2026-08-24T06:00:00Z",
  "completed_at": "2026-08-24T06:00:08Z",
  "modules": {
    "<nama_modul>": {
      "state": "complete | not_applicable | not_found | blocked_policy | blocked_robots | source_error | budget_exhausted | submission_error",
      "retry_count": 0,
      "final_timestamp": "<retrieved_at record atau completed_at>"
    }
  },
  "profile": { "...profil lengkap, lihat §5.2..." }
}
```

- `state` entitas: `complete` kecuali ada modul `submission_error` → `submission_error`. Perhatikan: perusahaan yang semua modulnya `not_found`/`source_error` tetap ber-state `complete` — "complete" berarti *terminal*, bukan *berhasil*.
- `retry_count` selalu 0 dalam praktik (tidak ada field `retry_count` yang pernah diisi di evidence record).
- `modules` hanya berisi modul yang diminta (`--modules`); modul yang tidak diminta tidak muncul sama sekali.
- Tidak ada field `errors[]` terpisah: kegagalan hanya terlihat sebagai state modul + `note` di evidence record.

### 5.2 Isi `profile` (per field)

| Field top-level | Asal | Keterangan |
|---|---|---|
| `organisation_number` | bulk | 9 digit, kunci |
| `name`, `legal_form`, `employees`, `bankrupt`, `liquidating` | bulk (`normalize_row`) | `employees` int atau null |
| `municipality`, `municipality_number` | bulk | dari `forretningsadresse.kommune*` |
| `industry_code`, `industry_label` | bulk | hanya NACE-1 |
| `website` | bulk | string mentah registry (bisa tanpa skema) |
| `latest_submitted_accounts` | bulk | tahun, string |
| `evaluation_split`, `sample_slice` | input batch | hanya bila ada di input |
| `evidence` | semua modul | dict per modul → evidence record (§5.3); kunci: `registry`, `accounting_obligation`, `registry_live`, `financials`, `roles`, `group`, `locations`, `website` (+ `financial_history` bila diminta) |
| `run_metrics` | batch | `{requests, bytes, latencies_ms[]}` per profil (jumlah request modul resmi + website) |
| `website_seed_source`, `website_seed_proof` | hanya bila seed diterapkan | dari `apply_verified_site_seeds.py` |
| `change_history` | tidak pernah diisi batch | hanya dibaca prototype; selalu kosong di output batch |

### 5.3 Evidence record (satu modul) — dataclass `Evidence` di `evidence.py`

```json
{
  "field": "financials",
  "status": "available | not_found | not_applicable | not_fetched | source_error | blocked",
  "source_type": "official_annual_accounts",
  "source_class": "official_annual_accounts",
  "source_url": "https://data.brreg.no/...",
  "retrieved_at": "2026-08-24T06:00:04Z",
  "value": { "...hasil normalizer, atau null..." },
  "as_of": null,
  "note": null,
  "content_sha256": "<hash 64-hex byte mentah, atau null>",
  "source_row_key": "<org-number, hanya registry bulk>",
  "effective_at": null
}
```

Catatan: `source_class` selalu disalin dari `source_type` (tidak ada taksonomi kelas terpisah di jalur resmi). `value` untuk `registry` = **seluruh baris CSV mentah** (90 kolom) — ini yang membuat #4 mungkin tanpa request baru. `value` untuk `group` = body JSON mentah. `value` untuk `website` = dict besar (requested/final URL, registered_domain, title, description, main_text_excerpt ≤5.000 karakter, social_links, structured_organisations, content_sha256, extraction_state, pages[], crawl_errors[], identity_assessment, discovered_social_links, social_link_assessments).

### 5.4 Run report (`--report`)

```json
{
  "run_id": "...", "started_at": "...", "completed_at": "...",
  "expected_count": 100, "emitted_envelopes": 100,
  "resumed_profiles": 0, "profiles_fetched_this_run": 100,
  "modules": ["registry", "..."],
  "registry": {"registry_snapshot_sha256": "...", "registry_rows_scanned": N, "requested": 100, "selected": 100},
  "operations": {"requests": N, "bytes": N, "p50_ms": N, "p95_ms": N},
  "validation": {"passed": true, "checks": {...}, "invalid_states": []}
}
```

Tidak ada: biaya pihak ketiga, daftar model/API, lisensi, asumsi hak sumber, perincian error per modul, total runtime eksplisit (dapat dihitung dari started/completed).

### 5.5 Cara refresh / change tracking bekerja

1. **Definisi field terlacak** — `refresh.TRACKED_FIELDS` (13 field): `registry.name/legal_form/employees/municipality/website/latest_submitted_accounts`, `financials.records`, `financial_history.years`, `roles.roles`, `locations.locations`, `website.title/description/social_links`. **Tidak terlacak:** grup, kontak, hash konten situs, halaman situs, observasi eksternal, accounting obligation.
2. **Diff** — `diff_profile(prev, curr)`: org-number harus sama persis (bila tidak → exception); tiap field dibandingkan dengan `==` mendalam; bila berbeda → satu event perubahan berisi `organisation_number, field, old_value, new_value, source_url, retrieved_at, effective_at, source_class, old_content_sha256, new_content_sha256, status` (dari evidence modul terkait di profil *baru*; `registry.*` memakai `registry_live` bila ada, jika tidak `registry`).
3. **Diff dataset** — `diff_datasets()`: keanggotaan org-number harus identik persis (bila tidak → exception); urutan diurutkan per org.
4. **Replay** — `run_refresh_replay.py`: mematerialisasi profil lama+baru dari snapshot byte evaluator (`SnapshotFetcher`, antarmuka `FetchResult` yang sama) lewat `fetch_official_modules` produksi, lalu menghitung presisi/recall terhadap `expected_changes` + `evidence_complete` (semua event harus punya source_url, retrieved_at, **effective_at**, hash lama+baru) + `idempotent_rerun` (`diff_datasets(curr, curr) == []`). Kualifikasi: presisi & recall ≥ 0,95 + evidence lengkap + idempotent.
5. **Idempotensi di batch** — resume (`--resume`) melewati profil yang `profile_complete_for_modules()` (semua modul diminta ada + status ≠ `not_fetched`); penulisan atomic via file `.tmp` + `replace`. Scrapy memakai JOBDIR + dedupe event.

### 5.6 Kesenjangan vs OUTPUT_CONTRACT.md

| Persyaratan kontrak | Status saat ini |

| Nilai hilang jangan jadi nol | ✅ Ditegakkan di normalizer/research/prototype |

## 6. Pertanyaan terbuka / ketidakpastian

1. **Rubrik otoritatif?** Kit (docs + `score_competition_v3.py`) memakai 55/15/10/12/8 external-first dengan target 80 dan sentiment 10 poin; brief memakai 50/30/12/8 (v2) dengan kualifikasi ≥65 dan precision 30 poin. Keduanya tidak bisa dipakai sekaligus untuk memprioritaskan. Perlu konfirmasi tertulis mana yang dipakai juri untuk tenggat 16 Nov — karena bila rubrik kit yang berlaku, family eksternal (termasuk sentiment) jauh lebih menentukan dan strategi "abstain sentiment" perlu ditinjau ulang.
2. **Anggaran waktu & ukuran official run tidak dipublikasi.** Tidak ada informasi batch resmi (100? 1.000?), batas waktu, spesifikasi mesin, atau batas egress. Ini menentukan: throttle `financial_history` (2,1 dtk × N), kedalaman crawl, pilihan urllib vs Scrapy, dan apakah konektor P3 muat dalam anggaran. Asumsi kerja: desain agar 100 perusahaan selesai nyaman dalam <30 menit di satu mesin kecil; ukur di smoke test.
3. **Format batch input resmi persis?** `read_organisation_inputs` menerima JSON (list atau `{"organisation_numbers": [...]}`), JSONL (dict ber-`organisation_number` atau string), atau txt. Bila format resmi berbeda (mis. kolom tambahan wajib, header, atau org-number berformat "123 456 789"), parser perlu disesuaikan. Juga: input buruk/duplikat saat ini menggagalkan SELURUH run tanpa envelope terminal — bila evaluator mengirim batch kotor, kontrak "satu envelope per input" tidak terpenuhi. Perlu kebijakan: tolak-keras (saat ini) vs envelope `submission_error` per input buruk.
4. **Snapshot sebelumnya untuk refresh:** apakah evaluator memasok previous-snapshot, atau submission harus menghasilkan + menyimpannya sendiri antar run? Menentukan desain #2 (argumen `--previous-profiles` vs penyimpanan snapshot internal).
5. **Bulk CSV: gzip atau plain?** `iter_bulk()` memakai `gzip.open` (gagal pada file plain), sedangkan README mengunduh `.../lastned/csv` ke `brreg-enheter.csv` tanpa dekompresi; test fixture secara eksplisit meng-gzip CSV sebelum dibaca. Kemungkinan server mengembalikan gzip terkompresi — verifikasi sekali dengan download kecil/header sebelum mengandalkan di mesin bersih.
6. **Skema respons live BRREG belum diverifikasi dari kode.** Nama field JSON live (entity/accounts/group/subunits) hanya terlihat lewat normalizer + fixture; perluasan normalizer (#5/#6/#7/#9) wajib diawali pengambilan satu respons live per endpoint (kecil, bukan bulk) untuk mengunci nama field. Batas rate endpoint selain history juga tidak diketahui.
7. **Apakah field bulk-only (aktivitas, kontak, kapital) dihitung sebagai recall oleh union evaluator?** Bila union dibangun dari crawler + submission lain yang juga memakai bulk, nilainya tinggi; bila union hanya dari sumber web, nilainya lebih rendah (tapi tetap >0 untuk synthesis/UX). Mempengaruhi urutan #4 vs #14/#17.
8. **Akseptabilitas sumber P3 di bawah "source policy" Builderr** (disebut README tapi tidak disertakan di kit): Wikidata, GDELT, RSS YouTube, Nominatim, NAV — perlu konfirmasi bahwa "permitted public page / open data" mencakupnya dan retensi evidence-nya diizinkan. Sampai ada konfirmasi, bangun dengan gate ketat + label sumber yang jujur.
9. **NAV feed: apakah registrasi konsumen + JWT melanggar "tanpa kredensial"?** Token publik eksperimen tersedia, tetapi ketergantungan pada token eksperimen rapuh; registrasi konsumen adalah akun (meski bukan "akun pribadi"). Keputusan koordinator diperlukan sebelum spike #22 dilanjutkan ke build.
10. **Mekanika submission:** email repo URL + run command + model/API + biaya ke `submit@builderr.ai` (README); belum jelas apakah prototype harus di-host (URL publik) atau cukup file HTML statis di repo, dan apakah laporan smoke-test 100 perusahaan punya format yang ditentukan. Juga belum jelas apakah evaluator menjalankan ulang dari repo (clean-machine) atau hanya menilai artefak yang dikirim.
11. **Status `financial_history` di mata evaluator:** bila modul ini tidak dijalankan, apakah klaim "tahun filing tersedia" dianggap hilang? Terkait #8 — aktifkan atau nyatakan eksplisit sebagai tidak dijalankan.
